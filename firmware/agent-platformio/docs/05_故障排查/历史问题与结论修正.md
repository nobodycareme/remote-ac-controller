# 历史问题与结论修正

本文件记录 DHT11/XHT11 温湿度链路排障过程中**先后被推翻的错误结论**，以正视听、
避免后人重蹈覆辙。核心教训：**先证伪测试方法，再下硬件结论。**

## 时间线与结论演变

### 阶段 A：DHT11 @ GPIO4 + 自定义驱动 —— 失败
- 现象：`dht_service.cpp` 自定义读取器下，握手前导正常（80/80/50µs），但 40-bit
  数据段总线卡高（bit-end-timeout）。0/12（t1000）、0/24（短杜邦线复测）。
- A/B 短杜邦线对照 `NO_CHANGE` → 排除线材长度成因（K16）。

### 阶段 B（错误假设，已推翻）：判为“主机侧 3.3V 供电完整性 / 总线 / GND 故障”
- 曾推断：背景中断致 3V3 跌落 / AMS1117 共载噪声 / 板载上拉或去耦问题。
- 一度给出硬件修复建议（100nF 去耦、独立 LDO、查焊点、万用表测中段电压）。
- **此结论已被阶段 D 推翻。**

### 阶段 C：换全新 XHT11，仍 @ GPIO4 + 自定义驱动 —— 仍失败
- XHT11 协议兼容 DHT11，前 ~20 bit 解码正常（Byte0≈0x28=40），第 ~21–23 bit
  同点卡高 —— 与旧 DHT11 同症。当时（第一轮）仍误判为主机侧故障。

### 阶段 D（决定性，2026-07-16）：XHT11 @ D1/GPIO5 + Adafruit 标准库 —— **20/20 PASS**
- 改用完全隔离环境 + 广泛验证的 **Adafruit DHT 1.4.7** 标准库，数据线移到 **D1/GPIO5**。
- 结果 `XHT11_TEST_SUMMARY total=20 valid=20 failed=0`，堆恒定、无复位。
- 同时审查旧测试与 `rawTrace()` 代码，确认：旧“卡高”证据无效（`Serial.print` 位于
  `noInterrupts()` 临界区，破坏单总线时序）。

## 当前归因（修正后的权威结论）
温湿度读取失败**并非**传感器损坏，**也不是**主机 3.3V 供电故障。需要明确区分两点：

1. **旧故障的主要问题是自定义 `dht_service`/`rawTrace` 测试方法存在缺陷**：其
   `rawTrace()` 在 `noInterrupts()` 临界区内调用 `Serial.print`，破坏单总线时序；
   自定义 bit-bang 时序也不稳。这一点已被代码审查与 Adafruit 对照测试确证。
2. **D2/GPIO4 是否存在独立异常，尚未进行 Adafruit 标准库单变量验证**：旧测试同时
   更换了“库（自定义→Adafruit）”与“引脚（GPIO4→GPIO5）”两个变量，无法隔离 GPIO4
   本身的贡献。因此**不把 GPIO4 定性为“唯一不稳定通道”，也不把 D1 定性为“唯一稳定
   通道”**。

当前正式方案采用**已经验证稳定的 Adafruit DHT 1.4.7 + D1/GPIO5**，且未再改动接线。
如需判断 GPIO4 是否独立异常，须单独做“Adafruit 库 + GPIO4”的单变量测试（用户未要求，
本轮未执行）。

改用 **Adafruit 标准库 + D1/GPIO5** 后：
- 阶段1 独立最小化验证：DHT11 **30/30 PASS**（`DHT11_GPIO5_MINIMAL_PASS`）。
- 阶段3 主工程稳定性：**133/133 PASS**（`DHT11_MAIN_INTEGRATION_PASS`）。

## 被推翻/废弃的东西
- ❌ “主机 3.3V 供电故障”假设（阶段 B/C 第一轮）。
- ❌ 硬件修复清单（100nF 去耦 / 独立 LDO / 换模块 / 查焊点）—— 与本次验证无直接结论，
  不将其作为已证结论。
- ❌ 自定义驱动 `dht_service.*`（阶段4 已删除）。
- ❌ “GPIO4 是唯一不稳定通道”“D1 是唯一稳定通道”这类过度定性表述。
- ❌ R1–R5 软件修复尝试（改错了对象，全部失败）。

## 关键教训
1. 底层诊断优先用**广泛验证的标准库**做对照，别只信自定义读取器。
2. 单总线 / 严格时序协议里，**临界区内禁止串口打印**等阻塞操作。
3. 换硬件结论前，先隔离“测试方法”变量（库、引脚、环境）。
