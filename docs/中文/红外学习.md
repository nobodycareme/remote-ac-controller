# 红外学习

如何为**你自己的**空调采集红外帧，并将其注册到固件（Firmware）中。

> **这一步必须由你完成。** 本仓库不附带任何真实红外帧数据。`cloud/backend/src/ac_states.ts` 中的状态目录描述的是一台特定的空调，无法控制你的设备。

## 1. 为什么采用学习方式而非协议库

空调遥控器发送的并不是离散的"开机"或"升温"事件。大多数遥控器在每一帧中发送**完整的整机状态** —— 模式、设定温度、风速、扫风标志、睡眠、定时 —— 编码成一段很长的连续脉冲串。以本项目开发时所对照的空调为例，250–450 字节的帧长十分典型。

由此产生的两个结论决定了系统设计：

1. **状态，而非增量。** 不存在可发送的"温度加一"命令。你需要为每一个想要到达的完整状态采集一帧。这就是系统将空调建模为离散的状态*目录*、而不是一组独立控件的原因。
2. **厂商专有编码。** 解码每个厂商的格式是一项庞大且脆弱的工程。采集并重放不透明的字节帧则与机型无关，且足够健壮。

代价也很直白：你只能到达已采集过的状态。

## 2. 前置条件

- 硬件已按 [`wiring.md`](./接线说明.md) 装配并验证完毕。
- 已刷入 public profile 的固件。
- 空调原装遥控器，电池可用。
- 串口监视器：在 `firmware/` 目录下运行 `./tools/dev.ps1 monitor`。

## 3. 串口 CLI 参考

交互式 CLI（`firmware/src/serial_cli.cpp`）提供以下命令。输入 `help` 可查看你当前构建中的权威命令列表。

| 命令 | 用途 |
|---------|---------|
| `status` | 设备整体状态 |
| `version` | 固件版本字符串 |
| `dht read` / `dht test` | 传感器健全性检查 |
| `ir probe` | 验证红外模块是否有响应 |
| `ir info` | 模块信息 |
| `ir learn` | 进入学习模式（模块内部槽位） |
| `ir send` | 重放已学习的帧 |
| `ir cancel` | 中止当前红外操作 |
| `ir extlearn` | 进入外部学习模式 —— 将帧采集到主机侧 |
| `ir extsend` | 发射当前暂存在设备上的帧 |
| `ir extload` | 将帧加载到暂存缓冲区 |
| `ir stage clear` / `append` / `commit` / `info` / `send` | 长帧的增量分段暂存 |
| `ir longframe` | 长帧采集辅助命令 |
| `ir stress` / `stressfixed` / `stressbounded` | 可靠性压力测试 |
| `ir setbaud` | 调整模块 UART 波特率 |
| `wifi connect` / `disconnect` / `scan` / `status` | 网络控制 |
| `net check` | 连通性探测 |
| `campus status` / `login` / `logout` | 可选的强制门户认证 |

## 4. 采集流程

针对**每一个**想要控制的状态：

### 第 1 步 —— 确认模块存活

```
ir probe
```

应收到识别响应。没有任何响应几乎总是意味着 UART 线未交叉 —— 见 [`wiring.md`](./接线说明.md) §1。

### 第 2 步 —— 将实体遥控器调到目标状态

利用遥控器自身的显示屏，把遥控器精确调到你想要的状态，例如*制冷 / 26 °C / 自动风 / 垂直扫风开*。此时先不要发送。

### 第 3 步 —— 启动采集

```
ir extlearn
```

模块进入接收模式。注意许多模块的采集超时只有几秒。

### 第 4 步 —— 发射

将遥控器保持在距**黑色**（接收）元件 3–10 cm 处，按下能够重发当前状态的按键。多数遥控器有专门的发送/确认键；如果没有，可以切换任意设置再改回来。

### 第 5 步 —— 验证采集结果

CLI 会报告所采集帧的长度与摘要。对同一状态**重复采集三次**并比对：

- 帧长必须完全一致。
- 摘要必须完全一致。

如果不一致，说明采集受到了环境红外污染（阳光、荧光灯、其他遥控器），或距离不合适。丢弃后重试。**绝不要注册未经复现验证的帧。**

### 第 6 步 —— 重放测试

```
ir extsend
```

将透明（发射）元件对准空调。空调必须精确进入所采集的状态。如果没有反应：

- 检查视距与距离（先从 1 m 以内开始）。
- 确认空调并非已处于该状态 —— 许多机型对空操作不会给出任何反馈。
- 对于长到需要分段传输的帧，尝试 `ir stage send`。

### 第 7 步 —— 记录

将帧字节、长度和 SHA-256 保存到你本地的私有目录。默认位置为 `<repo>/Private/Firmware/IR/Learned/<stateId>/`，该目录已被 git 忽略。可通过环境变量 `IR_LEARNED_ROOT` 覆盖。

**不要提交采集到的帧。** 除了泄露你的空调机型之外，公开的帧还会让红外覆盖范围内的任何人得以重放它。

## 5. 状态命名

使用稳定且具描述性的 `stateId`。本仓库的命名约定为：

```
<vendor>_<mode>_<temperature>_<fan>[_<modifiers>]_v<n>
```

示例：`acme_cool_26_auto_v1`、`acme_power_off_v1`、`acme_heat_22_quiet_swingV_v1`。

`_v<n>` 后缀允许你日后重新采集某个状态，而不破坏仍引用旧标识符的既有定时任务。

## 6. 注册状态

1. 从采集数据生成固件的 PROGMEM 注册表：

   ```powershell
   python firmware/tools/gen_ir_state_registry.py
   ```

   该脚本读取学习目录，并生成一个被 git 忽略、包含帧字节的 `.inc` 资源文件。

2. 在 `cloud/backend/src/ac_states.ts` 中更新对应的元数据。每个条目必须满足：

   | 字段 | 必须等于 |
   |-------|-----------|
   | `stateId` | 固件中的 `codeId`，须完全一致 |
   | `frameLength` | 采集到的字节数 |
   | `frameSha256` | 采集到的摘要 |
   | `mode` / `temperature` / `fan` / `swing*` / `powerOn` | 该状态的真实语义 |
   | `enabled` | 为 `true` 时才会在 UI 中展示 |

   长度与摘要不匹配是刻意设计的完整性校验：后端与固件必须就某个 `stateId` 所指代的帧达成一致。

3. 重新构建两端：

   ```powershell
   ./tools/build-all.ps1
   ```

## 7. 启用真实发射

真实红外发射默认在多个层面被禁用。启用方式见 [`security-model.md`](./安全模型.md) §5。概要如下：

- `WEB_REAL_IR_ENABLED` 控制受限的调试路径。
- `REAL_IR_PRODUCTION_CONTROL_ENABLED` 控制常规生产控制路径。
- 两者都只接受精确的字符串 `"true"` 或 `"1"`。

推荐顺序：先用 mock 确认应答做端到端验证；然后仅放行单个允许的 code ID 并设置较低的命令上限来启用调试路径；最后才启用生产控制。

## 8. 可靠性测试

在放心让系统无人值守运行之前：

```
ir stressbounded 50
```

该命令以受限的时序反复发射。注意观察 `ir_module_busy` 或 `ir_execute_failed` 确认应答。压力下偶发失败可以接受；持续的失败率则表明存在供电或接线问题 —— 见 [`hardware.md`](./硬件说明.md) §4。

## 9. 故障排查矩阵

| 症状 | 可能原因 |
|---------|-------------|
| `ir probe` 无响应 | TXD/RXD 未交叉，或模块未上电 |
| 多次采集帧长不一致 | 环境红外干扰；调暗灯光，靠近一些 |
| 采集成功但重放无效果 | 发射器指向不对、超出距离，或空调已处于该状态 |
| 10 cm 重放正常但 3 m 失败 | 供电电流不足 —— 见 [`hardware.md`](./硬件说明.md) §4 |
| ACK `ir_unknown_code` | `stateId` 不在固件注册表中；重新生成并重新烧录 |
| ACK `ir_state_disabled` | 该状态的 `enabled` 标志为 false |
| ACK `blocked_by_ir_policy` | 安全总开关（Kill switch）仍处于禁用状态 |
